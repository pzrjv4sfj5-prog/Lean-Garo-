## Work done this session

### 1. Root-caused the 9-key defect precisely

Read `pickPrimary` in full. The mechanism: `isVerified` (computed in
`normalizeFile`) is a regex anchored to the **start** of `notes`
(`^verified\/high`). A variant-tagged candidate's notes read
`"variant/VERIFIED/HIGH"` — never matches. This makes such candidates
invisible not just to the `verifiedNeutral` branch but to
`masterEntries` too, which is a flat last-write-wins over every
master-sourced candidate with **no confidence tag consulted at all**.
For `work`: candidates `Work/ga·a` and `Work/ka·a` (both
`variant/VERIFIED/HIGH`) lose to `Work/Kam` (`[OCR-flagged]`) purely
because `Kam` sits last in `master_dictionary.json`'s array order for
that key.

### 2. Fix (`prepare-data.js`)

- Two new per-entry flags computed in `normalizeFile` and threaded
  through `cleanedEntries` / `tagSource` / the source-merge dedup step:
  - `isVariantVerified` — `/^variant\/verified\/high\b/i` on notes.
  - `isWeak` — true when notes is empty, contains `unverified`, or
    contains `ocr-flagged`.
- New `pickPrimary` branch, placed **after** the existing
  `verifiedNeutral` check and **before** `masterEntries` (so it isn't
  bypassed by master-preference the way the old defect was):
  fires only when every non-variant candidate for the key is weak
  (no independent evidence of its own). Deliberately does **not**
  fire for `outside` — its neutral candidate `a'palo` carries its own
  `CONFIRMED` citation, not weak, left untouched.
  - Exactly one `variant/VERIFIED/HIGH` candidate → wins outright.
  - 2+ tied `variant/VERIFIED/HIGH` candidates → does not guess
    (same restraint as the existing `answer`-style neutral tie);
    excludes the weak value, falls back to last-write-wins among the
    verified candidates only, and records the tie (see §4).

### 3. Regression caught and reverted before shipping

First draft set `verifiedSelection: true` even for the new branch's
single-winner case. This silently defeated the existing
`grammarOverrides['smile']` entry — that override exists *because*
`Smile`/`ka·ding·sim·ik·a`'s notes are self-contradicting (`variant/
VERIFIED/HIGH` header, but the note body says "its status...is
unconfirmed...Not guessing"). Caught via the `grammarOverrides:
skipped 'smile'...` log line before committing anything. Fixed by
keeping `verifiedSelection: false` for this entire new branch — it's
a heuristic signal over the whole corpus, not the same trust tier as
`verifiedNeutral`'s narrow, hand-reviewed, anchored regex. Confirmed
`smile` still resolves to `Ka·dingsmita`.
